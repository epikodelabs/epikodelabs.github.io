Streamix FAQ ​

Answers to the questions that come up when adopting Streamix, each grounded in the runtime's actual behavior (current main / v3 atom & flow model).

Contents ​

  1. Cancellation and teardown: what happens when a consumer stops early, an Angular component is destroyed, or an async iterator is abandoned?
  2. Backpressure: which sources pace their producers, and how buffering or coalescing is selected.
  3. Error and completion: how exceptions, terminal states, and retries map from an RxJS mental model to the iterator model.
  4. Hot versus cold behavior, multicasting, and scheduling/time-based operators.

1. Cancellation and teardown ​

Streamix treats cancellation as a question of ownership. A consumer can detach without shutting down a source that others still use. When the last owner leaves, production stops for ordinary flows and shared sources; the atom retains its last state.

SituationWhat happensWhat you need to do
Consumer stops earlyThe consumer detaches. For flows / shared sources, production stops if it was the last owner.Call the unsubscribe function, or exit the for await loop.
Angular component is destroyedCompiled bindings are cleaned up automatically through DestroyRef.Explicitly clean up subscriptions and iterators created manually in component code.
Active async iterator is simply abandonedNo cancellation notification is sent. Subscriptions and resources can remain active.Close it with return(), usually in finally.

Three operations to keep apart ​

  • Unsubscribe: detaches one consumer and clears its queued deliveries.
  • Stop production: ends the producer (iterator is closed) while the atom keeps its last state.
  • Dispose: explicitly releases the atom’s resources, subscriptions, and disposal handlers (atom.dispose()).

Unsubscribing can lead to a producer stop for flows and shared sources, but it does not automatically dispose a plain writable atom.

When a consumer stops early ​

A subscription is a cleanup handle you can call:

ts
const unsubscribe = output.subscribe(value => {
  // Handle value.
});

await unsubscribe();   // or just unsubscribe()

The first call marks the subscription inactive immediately and runs teardown. Later calls are no-ops.

Removing one consumer does not necessarily stop the pipeline. If another subscriber still owns the output, production continues.

For flow-backed atoms and shared sources, the last subscriber leaving stops the producer (the underlying iterator is closed). The atom retains its last value; a later subscriber receives that retained value but does not restart the producer.

Plain writable atoms do not auto-stop or auto-dispose when the last subscriber leaves; they stay alive until you call dispose().

How cleanup travels through a pipeline ​

A pipe() call creates one new flow-backed output atom around a chain of iterator stages:

ts
const output = pipe(
  source,
  map(transform),
  filter(predicate),
);

The output atom owns the pipeline’s current value, subscriptions, and producer lifecycle. When the output stops, it closes the chain from the end back toward the source (return() is forwarded upstream). Operators that own resources (timers, buffers, inner iterators) must arrange their own cleanup; createOperator supplies upstream return() forwarding when an operator’s iterator does not define it.

Stopping one pipeline does not interrupt another pipeline that shares the same source. Detaching from a writable atom does not make that atom unusable.

Work already in progress ​

Streamix invalidates a stopped producer’s session so late results cannot produce new emissions from that output atom. A shared upstream source can still emit for its remaining consumers.

Cancellation cannot forcibly interrupt a JavaScript callback or promise that has already started. An asynchronous mapper, predicate, or subscriber callback may still finish and perform side effects.

A flow supplies an AbortSignal to its source factory. On cancellation it aborts the signal. Actually stopping external work requires cooperation: the operation must observe the signal, or the source must release its resources during cleanup.

When an Angular component is destroyed ​

Streamix’s compiled Angular integration connects view cleanup to DestroyRef. When the component is destroyed it removes source-reference observers, destroys compiled bindings and structural blocks, cancels scheduled rendering, and releases binding subscriptions.

These actions detach the view’s consumers. Producer shutdown then follows the same ownership rules: a shared source can continue for another component, while a flow losing its last owner stops.

Automatic cleanup covers the compiled bindings. A subscription created manually in component code needs its own lifecycle connection:

ts
const destroyRef = inject(DestroyRef);

const unsubscribe = source.subscribe(value => {
  // Handle value.
});

destroyRef.onDestroy(() => {
  void unsubscribe();
});

When an async iterator is abandoned ​

Exiting a for await loop ​

Exiting a for await loop with break, an enclosing return, or an exception thrown in the loop body invokes and awaits the iterator’s return() method when available:

ts
for await (const value of iterate(source)) {
  if (enough(value)) {
    break;
  }
}

const iterator = iterate(source);

Completion, finalization, and disposal ​

Operators can initiate cleanup too:

  • take(n) closes its upstream source as soon as it receives the nth value.
  • finalize(callback) runs its callback on completion, error, or explicit iterator closure.

For a broader cleanup boundary, dispose of the output atom:

ts
await output.dispose();
1

Disposal stops production and releases the atom’s subscriptions and disposal handlers. It does not indiscriminately dispose an upstream source that still has other owners.

2. Backpressure ​

It depends on the source model. Flow-backed atoms run at the source’s pace: consumers cannot block the producer. Shared sources are push-based — their connect function receives an awaitable push — so a producer that awaits it is paced by consumers. That is the runtime’s only blocking backpressure.

Source kindProducer paced by consumers?Slow consumer behavior
Flow-backed (flow, pipe, from, …)NoPer-subscriber FIFO queue (unbounded); mode: "analog" keeps only the latest pending value
Shared source (createSharedSource, timer, interval, addListener, DOM)Yes, when connect awaits push in discrete modepush waits for buffer space and for subscriber callbacks to finish; async iterators queue values instead of applying backpressure

The atom’s .value always reflects the newest emission.

Delivery mode (the primary control) ​

Flows and shared sources expose the same delivery mode:

ts
const positions = flow(pointerPositions(), { mode: "analog" }); // latest pending value
const clicks    = flow(clickEvents(),      { mode: "discrete" }); // every event
1
2
  • mode: "discrete" (default) preserves every emission.
  • mode: "analog" keeps only the latest pending value (ideal for pointer, scroll, or other high-frequency signals where intermediate values do not matter).

Shared sources also own a single cyclic buffer with an optional capacity:

ModeDefault capacityFull-buffer behavior
discrete16push waits for a free slot (producer waits)
analog1Overwrites the pending slot (latest wins)

Flows have no source-side buffer — mode: "analog" conflates each subscriber’s pending queue instead. Keeping the queue per-subscriber preserves fan-out isolation: one slow subscriber on a flow does not stall the source or the other subscribers.

There is no public per-consumer capacity / overflow option on subscribe() or iterate() in the current API. Buffering and coalescing are handled by the delivery mode and the runtime’s internal buffers.

Blocking backpressure (shared sources only) ​

A push-based producer can be paced, but only cooperatively:

  • In discrete mode, push(value) settles after the ring buffer accepts the value and subscriber callbacks finish processing it. Promise-returning callbacks are awaited, so a slow async subscriber delays push — and, for timer / interval, the next tick. Because distribution is shared, that subscriber also delays every other consumer.
  • In analog mode, push overwrites the latest pending value and returns immediately; consumers never slow the producer.

DOM event sources cannot be paced by the browser: addEventListener ignores the listener’s returned promise. Awaiting push in discrete mode preserves events by queueing pending listener invocations, so memory grows with the backlog regardless of the ring-buffer capacity. Use mode: "analog" for high-frequency streams; pointer and scroll streams already do.

Subscriber queues and iterators ​

On atom-backed sources (writable atoms, flows, derived atoms), each subscription owns a private pending queue:

  • An async callback is never re-entered; later values wait until the previous invocation settles.
  • Default (discrete) delivery is FIFO and lossless for the life of the subscription.
  • Analog delivery keeps only the latest pending value for a busy subscriber.

atom.next() / .set() are synchronous and never wait for subscribers.

iterate() and for await own a separate per-iterator buffer: discrete values queue without a bound, analog atoms conflate into it. Consuming slowly never pressures a flow producer, and it does not pressure a shared-source producer either — a shared source’s ring buffer drains into this queue, so only async subscriber callbacks suspend its producer.

Choosing a mode ​

  • Every event matters and the producer can wait: keep the default discrete mode. Built-in timer sources await push; a custom connect should do the same so a full buffer suspends the producer.
  • Only the latest value matters, or the producer cannot wait (DOM): use analog; intermediate values are conflated and the producer never blocks.
  • A flow producer must not outrun its consumer: do not rely on the runtime to pause it. Use mode: "analog", operator-level shaping (buffer, bufferCount, debounce, throttle, sample), or make the producer pace itself (await inside the generator).

3. Error and completion ​

In RxJS an error terminates an Observable. In Streamix failure is a state the atom carries, and termination is a policy:

ts
const status = atom("idle", {
  onError: handler,           // source and subscriber failures
  terminateOnError: false,    // true disposes the atom after a producer/formula failure
  propagateErrors: false,     // true rethrows after handlers run
});
1
2
3
4
5

Failure ​

  • A producer or formula failure sets .error, makes .value throw, and notifies onError handlers. The atom stays undisposed unless terminateOnError: true.
  • .safeValue never throws; it returns the last retained value (or the NO_INITIAL_VALUE sentinel before the first emission).
  • Subscriber callback failures are isolated: other subscribers keep receiving values and the atom’s .error stays empty. For compatibility, onError handlers also observe subscriber failures.
  • Writable atoms and flows leave the error state through recover() / clearError(); next(value) after recovery publishes normally. fail(error, { terminate: true }) enters the state terminally.
  • Derived atoms always record errors; the first failure invalidates downstream formulas, whose reads rethrow. The next successful upstream emission restores them.

Iterators ​

next() rejects while the atom is in its error state, after any accepted values have been drained. An iterator retains the terminal error it observed even if the atom later recovers, so one consumer’s iteration ends deterministically while the atom keeps serving others.

Completion ​

A completed producer ends iteration with { done: true }; it does not dispose the atom. The atom retains its final value, late subscribers replay it, and late iterators replay it once before finishing. A completed from([1, 2, 3]) gives a late consumer only 3 — the current value, not a replay of the sequence.

4. Hot versus cold, multicasting, and scheduling ​

Streamix has no separate Observable type: pipe() and every factory produce an atom, and atoms are stateful. Every non-disposed atom that has emitted replays its current value to a new subscriber before future emissions. A plain atom therefore behaves more like an RxJS BehaviorSubject (or a source shared with shareReplay(1)) than like a cold Observable.

One producer per atom ​

  • flow(factory), from(value), and defer(factory) create one producer per atom instance. The factory runs when the producer activates (first subscriber / first pull), not once per subscriber. All subscribers share that single producer.
  • Cold behaviour lives in the factory call: each call to flow(...), interval(...), from(...), etc. creates a separate cold-to-hot instance with its own producer and state.
  • After the last consumer leaves (or the producer completes), the producer stops and the atom freezes. A later subscriber replays the retained value but does not restart the producer.

Multicasting ​

Streamix multicasts in three related ways:

  1. Every atom is already a multicast point
    Subscribing or iterating an atom never re-runs its producer. New consumers receive the current value (if any) and then live emissions. This is the default for pipe(), flow(), writable atoms, and derived atoms.

  2. Shared sources (resource-level multicasting)
    Factories such as timer, interval, addListener, DOM on, and the lower-level createSharedSource own one underlying resource. They are ref-counted:

    • first consumer starts the resource,
    • last consumer leaving stops it and runs cleanup. Delivery mode (analog / discrete) and an optional ring-buffer capacity are configured once on the shared source; every consumer sees the same sequence (or the same coalesced latest value).

  3. Pipeline operators share() and shareReplay()

    • share() connects to the upstream source the first time the shared pipeline is consumed. It disconnects (calls upstream return()) only when the last consumer calls return().
      Important: a consumer-injected throw() does not release the shared connection — only return() is treated as definitive teardown, because an injected error may be recoverable. An upstream failure, by contrast, fails and disposes the shared atom.
    • shareReplay(n) does the same connection/disconnection bookkeeping and additionally keeps a bounded history so late consumers receive the last n values before live emissions.
    • Without share / shareReplay, each independent for await (or each pipe that is not shared) over a cold iterable obtains its own upstream iterator.

Multi-source topologies are provided by factories and higher-order operators: merge, concat, zip, combineLatest, race, forkJoin, and mergeMap / switchMap / concatMap / exhaustMap. These also share the underlying sources according to the rules above once the sources themselves are atoms or shared sources.

Scheduling and time ​

  • Time operators use the real clock: timer(delay, interval?) and interval(ms) are shared sources over setTimeout / setInterval; debounce, throttle, delay, and sample use real timers too.
  • There is no RxJS-style scheduler parameter on those operators. For deterministic tests, install fake timers (jasmine.clock(), vi.useFakeTimers()) before creating the atom.
  • observeOn('microtask' | 'macrotask' | 'idle') selects the task queue a value is delivered on; values produced before the first subscriber attaches are dropped, so pair it with shareReplay when replay matters.
  • setScheduler / getScheduler replace the runtime’s propagation scheduler (the depth-ordered flush of reactive updates), not timer scheduling. transaction(fn) batches several writes so downstream formulas publish once.
  • mode: "analog" versus "discrete" is the scheduling-like choice that matters most for event sources: analog conflates to the latest pending value, discrete preserves every event.
